# Assessment outputs

Every run produces the same six outputs plus an update check, all generated by one script
from one file, `.appaudit/findings.json`. Do not hand-write the brief or the report.

## 1. Load the rules

Read, from `${CLAUDE_PLUGIN_ROOT}/skills/assess/references/`:
`findings-schema.md` (the fields), `report-template.md` (what each output contains),
`scoring-and-triage.md` (CVSS-BTE, SSVC, EPSS, KEV, timelines) and `regulatory/index.md`
(jurisdiction selection and the two flag tiers). `findings-example.json` in the same
folder is a complete worked example.

## 2. Collect findings

Take the findings from this session. For each, gather: title, location (file and line for
code), evidence-log `seq` numbers, proof steps, root cause, impact, CVSS v4.0 vector, SSVC
decision points, CVE IDs, remediation with a copy-paste patch, re-test step, and the
assessor's confidence.

## 3. Verify independently

Send the findings to the `appaudit:verifier` agent; several findings may go in one call.
Pass the finding text and evidence pointers, not your reasoning about why the finding is
real. Record its verdict in each finding's `verifier` field and apply it:

| Verdict | Action |
|---------|--------|
| Confirmed | Report as Confirmed |
| Likely | Report as Likely, with what proof would be needed |
| Needs evidence | Gather the evidence it names and verify again, or report as Likely |
| Rejected | Move to `verified_not_applicable` with the verifier's reason, or drop it if it was a misreading |

Never set a confidence level higher than the verifier's verdict; the builder refuses to
build if you do. Apply its CVSS vector corrections before scoring.

## 4. Score, look up, flag

- Compute each CVSS-BTE score with the FIRST v4.0 calculator. Run `/appaudit:intel` (or
  `vuln_intel.py`) for KEV, EPSS and `calculator_url`. A KEV-listed finding is never below
  SSVC Attend.
- Set `timeline` from the KEV due date (BOD 26-04), PCI DSS 6.3.3 where it applies, or
  `organisation-defined`.
- Send the verified findings and the scope file's jurisdiction profile to the
  `appaudit:regulatory-mapper` agent. Save its JSON to `.appaudit/candidates/regulatory.json`
  and apply it:

  ```bash
  python3 -I "${CLAUDE_PLUGIN_ROOT}/skills/assess/scripts/merge_candidates.py" --findings .appaudit/findings.json --regulatory .appaudit/candidates/regulatory.json
  ```

  Review its flags before applying: each needs the facts in `basis`, tier `may_trigger_now`
  or `readiness`, and `decided_by` `client/counsel`. Never state that a notification is
  required. With no profile, the mapper adds no flags and lists the jurisdictions as not
  assessed (the builder also derives the uncovered jurisdictions from the profile).
- Check disclosure routing against `regulatory/disclosure.md` and record any conflict.

## 5. Write findings.json

Fill `engagement` from `.appaudit/scope.json` (authorization, mode, window, scope,
jurisdiction profile) and the session (capabilities used, threat-intel date, areas not
tested). Redact secrets and personal data to the last four characters. Write the file to
`.appaudit/findings.json`. Writing it is not a protected change, so no approval prompt
appears.

## 6. Build the outputs

```bash
python3 -I "${CLAUDE_PLUGIN_ROOT}/skills/assess/scripts/build_outputs.py" \
  --findings .appaudit/findings.json --scope .appaudit/scope.json \
  --evidence .appaudit/evidence/evidence.jsonl --out .appaudit/reports \
  --plugin-root "${CLAUDE_PLUGIN_ROOT}" --update-source "${user_config.update_source}"
```

Run it exactly in this form, as one command with no `&&`, pipes or redirection, so the scope
guard recognises it as the plugin's own script and does not ask for approval. If `python3`
is not found, use `python`. The script verifies the evidence chain itself and reuses the
Step 0 update-check result saved in `.appaudit/update-check.json` (same day), so it makes no
second network call. For a re-test, add `--previous <earlier run folder>/findings.json`; the
outputs then include `delta.md` and `delta.json` (or use `/appaudit:retest`).

- Exit code 2 means `findings.json` has errors and nothing was written: fix every listed
  error and run it again.
- Warnings are printed and listed in the report appendix; resolve the ones you can.
- If the evidence chain failed, say so first when you report back.

## 7. Report back

Tell the user, in this order:

1. Any `may_trigger_now` flags (finding, instrument, deadline, authority), for client or
   counsel to decide.
2. The output folder and the six files, plus `update-check.json` and `MANIFEST.sha256`.
3. Totals by severity and SSVC decision, and what the verifier rejected.
4. The update-check result from Step 0 (already given as the first line of the session):
   repeat it only if an update is available or the bundled data is stale.

Do not describe any output as a certification or a compliance attestation.
